# 2026-11-03 鼠标卡顿排查

## 当前结论

未复现或证实 LitePulse 导致系统鼠标卡顿。用户补充：主界面、预览均关闭时也会卡，且与 Codex 活跃有关。目前应优先做 Codex 退出前后的对照，不能仅凭采样频率或平均 CPU 占用确定原因。

本次不改变 LitePulse 产品行为，不替换 `dist/litepulse.exe`。增加一个默认忽略的原生性能诊断测试，便于复测后台与交互采样路径。

- 初始沙箱内 PDH 无法访问，发生 NVML 回退，该轮数据不用于判断。以下数字来自真实用户会话；独立 20 秒 probe 确认 GPU 使用 PDH，磁盘计数器可用。

## 采样与托盘耗时

先运行优化构建的 `--probe 20`，完整采样通常约 1～2 毫秒，GPU 通常约 0.8 毫秒，没有观察到长时间采集阻塞。

随后运行 89 秒的原生诊断，复用真实 `App` 消息处理、采样线程和 Shell 托盘更新。三个阶段均不展示主窗口或预览；交互阶段使用菜单状态激活同一套加速策略，从而隔离绘图开销。

| 阶段 | 时长 | 样本数 | 完整采样平均 / 最大 | GPU 平均 / 最大 | 主线程样本处理平均 / 最大 |
|---|---:|---:|---:|---:|---:|
| 后台 30 秒 | 33 秒 | 2 | 1.757 / 1.815 ms | 0.986 / 0.988 ms | 0.869 / 1.070 ms |
| 激活 1 秒 | 23 秒 | 23 | 1.755 / 3.908 ms | 1.024 / 2.521 ms | 1.126 / 8.769 ms |
| 恢复后台 30 秒 | 33 秒 | 2 | 1.393 / 1.462 ms | 0.735 / 0.805 ms | 1.102 / 1.567 ms |

主线程耗时包含历史更新和 `Shell_NotifyIconW`，最大 8.769 ms 是整段处理耗时，尚未归因于某个子调用。恢复后台后样本数符合慢速采样，未观察到持续 1 秒采样失控。GDI / USER 对象在三个阶段均保持 7 / 8，短测未见对象增长。

诊断的 10 ms 消息轮询最大间隙为 19.019 ms。这不是鼠标输入、DPC 或呈现延迟测量，不能据此排除驱动/合成器延迟。诊断自身轮询和初始化会影响 CPU 占用，因此不将其进程 CPU 数字当作正式产品基线。

## 代码中的优化空间

1. `Preview::update` 在每个可见样本更新时重复设置四项 DWM 材质/边框属性。可按初始化、主题或合成状态变化更新；这只影响预览开启时，不能解释所有界面关闭时的卡顿。
2. `Tray::update` 即使只有 tooltip 改变也设置 `NIF_ICON` 并再次提交旧图标。可在图标内容实际变化时才携带此标记，减少不必要的 Shell 图标更新。其对鼠标响应的收益尚未测得。
3. 每次切换间隔都会发 `Wake`，当前语义是立即采样。快速进出托盘时，恢复较慢间隔也会触发一次采样，可考虑合并待处理唤醒或区分加速和降速，避免交互抖动造成额外采样。此次三个稳定阶段未发现采样失控。

以上是代码层面的优化候选，不作为已定位的卡顿原因，也没有在本次盲目修改。建议先在保持 LitePulse 配置不变的情况下，完整退出 Codex 后观察，再打开 Codex 对照；随后才决定是否需要驱动级跟踪或针对性修复。
